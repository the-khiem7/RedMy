# Redmine Worklog - Generate Drafts

Draft new worklogs for the gap from the checkpoint to today. **Never call `smart_log_time`/`create_time_entry` in this skill** - finish by handing over to the `redmy-apply` skill. Read `references/rules.md` in this skill before drafting any row - it is a list of mistakes the user has rejected many times in the past, so do not draft from memory. The format of every project file is defined in the `redmy-bootstrap` skill's `references/schemas.md` (installed next to this skill).

## Arguments

No argument: the window of each issue runs from its checkpoint to today. `<day...> /<month>` (for example `02 03 04 /11`) drafts only those days of that month in the current year. Each named day replaces the issue's checkpoint start for that day alone, and steps 2 to 8 apply unchanged, so cited commits are still dropped and the day cap still holds. A named day that already has a row on an issue is shown to the user and not drafted again on that issue unless they ask.

## Steps

0. If `task-registry.md` or `checkpoint.md` is missing, or the registry frontmatter lacks `redmine_user`, `redmine_base_url` or `tracking_since`, stop and tell the user to run the `redmy-bootstrap` skill first. If `last_synced` is missing or more than 3 days old, re-run the steps of the `redmy-sync` skill first, inline, without the user having to call it separately.
1. Read `checkpoint.md` to get each issue's `Last Logged Date` - this is the real stopping point (counting only rows that were actually logged, not draft/skipped rows). An issue with no row starts at `tracking_since` from the registry frontmatter, never earlier.
2. Collect every commit SHA already cited in the Evidence column of any `history/*.md` row - logged, `Not logged` or skipped, in every issue's file - expanding a cited range `<a>..<b>` with `git rev-list <a>^..<b>` on its repo. These commits are already spoken for. Reason: one repo serves several issues and each issue has its own checkpoint, so the window of one issue re-covers commits already logged under another.
3. Read `git-identity-map.md` to know which git author name on each repo is the user. If an unfamiliar author name appears on a known repo, it is not certain to be the user - ask the user to confirm before counting it, then add a new row to `git-identity-map.md`. For a repo with no row yet, list the distinct authors of the window (`git log --format='%an <%ae>' | sort -u`) and ask which of them are the user before reading any commit.
4. For each issue with a gap (Last Logged Date, today]: skip an issue whose Repo/Source is `*(not yet determined)*` and name it in the step 8 report, and draft only self-reported rows for one whose Repo/Source is `none`. Otherwise run `git log` on the repo(s) mapped in the Repo/Source column of `task-registry.md`, filtered by author = the user (step 3), from the day after the checkpoint, and drop the SHAs collected in step 2. A commit belongs to the date of its commit as `git log` shows it, in local time - also after midnight; work the user remembers doing on another day is a self-reported row.
5. Assign commits to issues:
   - Read the issue's Constraints column in `task-registry.md` and `decisions.md` first - many ambiguous cases already have an answer there (e.g. which issue excludes whose work, which submodule is not counted).
   - If one day/one commit has content belonging to multiple issues, read the actual diff/file content (not just the commit subject) to split the hours by proportion - do not assign the whole day to one issue out of "convenience".
   - If unsure which issue fits (unfamiliar system name, a codename that matches no task), look up Redmine (`list_issues`/`list_projects`) for a matching issue before guessing. Once resolved, record it in `decisions.md`.
   - Do not consider history inside a git submodule when assessing effort - only count commits at the level of the repo listed in Repo/Source (see the matching entry in `decisions.md` as an example).
5a. Optional, interactive session only. For each day of the window still thin or empty after step 5, list the agent's session transcripts of that local date (Claude Code keeps them as `*.jsonl` files in its `projects` directory, one folder per repo, with UTC timestamps - convert to local time) and read their first requests, to find work that left no commit: console changes, reviews, planning, work in a repo not mapped to an issue. Put what you find to the user as a candidate self-reported row. It is never hours by itself, and never quote a credential a transcript may contain. Reason: a day of reviews, planning or console work has no commit, so git-only drafting leaves that day short or asks the user to remember it cold.
5b. Optional, interactive session only, for a day still thin or empty after steps 5 and 5a, and only when the user agrees: check whether the user's own AWS identity touched an account that day.
   - Profiles: the rows of `aws-identity-map.md` (defined in the `redmy-bootstrap` skill's `references/schemas.md`) for the repos of the issues involved, or the profiles the user names; with neither, ask. Take profile names from `aws configure list-profiles`; never open the AWS config file or the AWS shared-credentials file.
   - Name the profile in every command. First `aws sts get-caller-identity --profile <profile> --query "[Account,Arn]" --output text`; when it fails the SSO session has expired - skip that profile, say so, and ask the user to log in themselves. Then `aws cloudtrail lookup-events --profile <profile> --region <region> --start-time <local midnight as UTC> --end-time <next local midnight as UTC> --lookup-attributes AttributeKey=Username,AttributeValue=<CloudTrail Username>`, once for the profile's own region and once for `us-east-1`, where the global IAM and CloudFront events appear. For a local day at UTC+7, 02 Nov runs from `2026-11-01T17:00:00Z` to `2026-11-02T17:00:00Z`.
   - CloudTrail Username is the session name for an SSO profile (the user's email) and the IAM user name for a static-key profile; read it from the Arn above and confirm it with the user. Filter by `Username` and nothing else: a lookup takes one attribute, and `ReadOnly=false` returns mostly the write calls of instance and service roles while hiding the read-only work (observed: 730 such events against 42 of the user's).
   - Event history keeps 90 days of management events, so an older day proves nothing. Lookups are limited to 2 per second per account per Region: run them one after another.
   - Report the event count, the first and last time in local time, and the most frequent `eventSource:eventName` pairs; never print an access key, session token or request parameter. No events means "no events for <Username> in <profile>", never "no work": the history sees only the user's own sessions, and work reached through another credential does not show under this Username.
   - It shows presence, not effort. Hours still come from commit times or the user's own account. A row whose only basis is CloudTrail is a self-reported row with `[needs confirmation]`, and its Evidence names the profile, the account id and the first and last event time.
   - When the user confirms a new profile-to-repo pairing or its Username, add a row to `aws-identity-map.md`.
   - In an unattended run (no user to agree, no SSO login possible) skip steps 5a and 5b without error and name them as skipped in the step 8 report.
6. Draft each working day as 1 row: Date, Hours, Activity, Redmine Comment (see `references/rules.md` for style), Worklog = `Not logged`, Evidence = real commit SHA (or "Self-reported by the user - no commit" if the user recounted it verbally; a step 5b finding is appended as `CloudTrail <profile> (<account id>) <first>-<last> <time zone>`). The Hours of one date across every issue - rows already in any `history/*.md` file plus the rows drafted now, not counting `**Skipped**` rows - add up to 8.0 at most; a day with less evidence stays short and is asked about, never topped up to 8 unless the user asks for it (see rule 1 in `references/rules.md` for how such hours are recorded). Weekend days or leave days only count hours when the user explicitly confirms, never by inference; write that confirmation into Evidence (e.g. `weekend confirmed by the user`), because `redmy-apply` lint fails a weekend row without it. Attach the label **[needs confirmation]** at the end of the Redmine Comment for any row where the issue assignment or the number of hours is a judgment call and not certain - so the user sees it right at approval time, not only in the agent's head.
7. Append the draft rows to the corresponding file `history/<issue-id>-<slug>.md` (create a new file if that issue has real work hours for the first time - do not pre-create empty files for issues with 0h). Do not edit/delete old rows.
8. Finish by presenting the whole draft table by day to the user, list the issues that were not scanned because their Repo/Source is undetermined, name which of steps 5a and 5b ran and which were skipped and why, and state clearly: run the `redmy-apply` skill next to log for real.

## Do not

- Do not take hours from a session transcript or from CloudTrail events: they show presence and a time span, not effort - see rule 1 in `references/rules.md`.
- Do not run any `aws` command in step 5b other than `sts get-caller-identity` and `cloudtrail lookup-events`, and never `aws sso login` or any write.
- Do not call any Redmine MCP write tool (`smart_log_time`, `create_time_entry`, `create_issue`, `update_issue`) - not this skill's job.
- Do not add hours on your own for a day with no evidence (a commit or the user's own account) - better to leave it blank and ask than to guess.
- Do not describe the Redmine Comment with internal terminology (report file names, release branch names, internal tool names) - see `references/rules.md`.
